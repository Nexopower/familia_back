DOCUMENTACIÓN BACKEND - familia_back (NestJS + SQL Server)
=====================================================

1) Resumen
---------
Este proyecto es una API REST construida con NestJS (TypeScript) que se conecta a SQL Server mediante el paquete `mssql`.
Incluye autenticación con JWT (access + refresh), soporte multi-negocio (multi-tenant) y módulos funcionales:
- Auth (login, logout, switch de negocio, validate token, hash de password)
- Dashboard (vista general agregada por negocio)
- Productos
- Inventario
- Facturas
- Reservas
- Contabilidad

2) Requisitos
-------------
- Node.js (recomendado: LTS)
- SQL Server (instancia accesible desde donde corre el backend)

3) Configuración (.env)
----------------------
Crear un archivo `.env` en la raíz con:

PORT=3000

DATABASE_USERNAME=...
DATABASE_PASSWORD=...
DATABASE_HOST=...
DATABASE_PORT=1433
DATABASE_NAME=...

Notas:
- La configuración se carga con `@nestjs/config` desde `src/sql/config/configuration.ts`.
- En la configuración actual, `encrypt` está en false y `trustServerCertificate` en true.

4) Cómo ejecutar
---------------
Comandos útiles (ver `package.json`):
- Desarrollo (watch): npm run start:dev
- Build: npm run build
- Producción: npm run start:prod

La app levanta en el puerto indicado por `PORT` (o 3000 si no existe).

5) Conexión a base de datos
---------------------------
Servicio: `src/sql/sql.service.ts`
- executeQuery(query): ejecuta un query simple y devuelve recordset.
- executeQueryParams(query, params): ejecuta query con parámetros.
- beginTransaction/queryTransaction/commitTransaction/rollbackTransaction: helpers de transacción.

6) Autenticación y seguridad
----------------------------
6.1 JWT
- Se usan access tokens (15 min) y refresh tokens (7 días o 30 días según parámetro interno).
- El JWT se firma con un secreto definido en `src/const/const.ts` (Tokenpass.secret).
  IMPORTANTE: actualmente el secreto está hardcodeado.

Claims del JWT (payload):
- sub: string (codusr)
- codrol: number|string|null (rol principal o rol por negocio)
- codneg: number|null (negocio seleccionado; puede ser null en sesión "vista general")
- audit: number|null (id de auditoría; en este proyecto se toma desde codper)

Guard:
- `src/auth/guards/jwt-auth.guard.ts`:
  - Lee Authorization: Bearer <token>
  - Valida token (firma + blacklist) con TokenService.ValidatedToken
  - Adjunta payload en request.user

6.2 Refresh tokens y revocación
- Refresh token se guarda en tabla `refresh_tokens`.
- Revocación de access token: se agrega el token a `token_blacklist` con fecha de expiración.
- Limpieza automática: `TokenCleanupService` corre cron 2 veces al día (00:00 y 12:00) y borra tokens expirados.

Nota: En el código existe `TokenService.RefreshAccessToken(refreshToken)` pero NO hay endpoint expuesto actualmente para refrescar el access token.

6.3 Multi-negocio (multi-tenant)
Reglas clave:
- El usuario se autentica principalmente por `nombre_usr` + `passwo_usr` (también soporta codusr por compatibilidad).
- La pertenencia a negocios se define por:
  - dbo.usuario_negocio (asignación de usuarios a negocios)
  - dbo.negocio_dueno (dueños/codueños)
- Validación de acceso por negocio:
  - `AuthService.assertCanAccessNegocio(payload, codneg)`
  - SUPERADMIN tiene bypass.

Tipos de login soportados (comportamiento implementado):
A) Admin global (SUPERADMIN o usuario codusr='admin')
- Puede ver todos los negocios.
- Puede iniciar sesión sin enviar codneg.
- Puede cambiar de negocio con /auth/switch-negocio.

B) Dueños (usuario.esdueno_usr = 1)
- Puede iniciar sesión sin enviar codneg (sesión "vista general").
- Puede cambiar de negocio con /auth/switch-negocio.

C) Trabajadores
- Si loginmulti_usr = 1:
  - Puede iniciar sesión sin codneg (vista general).
  - Puede cambiar de negocio con /auth/switch-negocio.
- Si loginmulti_usr = 0:
  - DEBE enviar codneg en login.
  - NO puede cambiar de negocio sin volver a iniciar sesión (switch-negocio devuelve error).

  Body:

      "codusr": "...",        // opcional
      "nombre": "...",        // opcional

  - Debes enviar `codusr` o `nombre`.
  - Para trabajadores sin loginmulti y no dueños: codneg es obligatorio.

  Respuesta (ejemplo):
    {
      "accessToken": "...",
      "refreshToken": "...",
      "user": {
        "codusr": "...",
        "codper": 123,
        "codrol": 2,
        "codneg": 1,           // puede ser null si sesión general
        "nombre": "...",
        "esdueno": true,
        "loginmulti": true,
        "isAdmin": false
      },
      "negocios": [
        {"codneg": 1, "nombre": "...", "esdueno": true, "esprincipal": true}
      ]
    }

- POST /auth/switch-negocio (PROTEGIDO)
  Body:
    { "codneg": 1 }

  Reglas:
  - Solo SUPERADMIN, dueños o usuarios con loginmulti.
  - Verifica pertenencia al negocio.

  Respuesta:
    {
      "accessToken": "...",
      "expiresIn": 900,
      "codneg": 1,
      "codrol": 2
    }

- GET /auth/validate
  - Valida el token actual (lee Authorization header).
  - Respuesta: payload decodificado.

- POST /auth/logout
  - Revoca el access token actual agregándolo a blacklist.
  - Respuesta:
    {"SUCCESS": true, "CODE": "TOKEN_REVOKED"}

- POST /auth/hash-password
  - Genera un hash determinístico para una contraseña.
  Body:
    { "password": "texto" }
  Respuesta:
    { "password": "texto", "hash": "..." }

Notas de hashing:
- Se usa AES-256-CTR con IV fijo y clave derivada (scrypt) en `src/class/encryption.class.ts`.
- El resultado se trunca a 100 caracteres hex.

Módulos, componentes, permisos y visualización (RBAC)
----------------------------------------------------

IMPORTANTE (estado actual del backend):
- El backend hoy expone un catálogo y visibilidad de módulos basado en las claves del archivo `src/rbac/rbac.permisos.ts`.
- La estructura y nombres de permisos puede extenderse libremente en BD (tabla `dbo.permisos`) usando claves string tipo `MODULO.ACCION`.
- En el catálogo actual están definidos: DASHBOARD, PRODUCTOS, INVENTARIO, FACTURAS, RESERVAS, CONTABILIDAD y USUARIOS.
- Nota de naming: en este backend se usan claves `FACTURAS.*` (no `FACTURACION.*`) y `CONTABILIDAD.INGRESO.CREAR`/`CONTABILIDAD.EGRESO.CREAR` (singular).

La sección siguiente describe el enfoque RBAC y un mapa recomendado (útil para front/back).

## Módulos, componentes, permisos y visualización (RBAC)

### 1) Conceptos (RBAC)
El control de acceso se basa en **permisos** (tabla `dbo.permisos`) asignados a:
- **Roles** (tabla `dbo.roles`) vía `dbo.rol_permiso`
- **Roles globales por usuario** vía `dbo.usuario_rol_global`
- **Permisos globales directos por usuario** vía `dbo.usuario_permiso_global`
- **Roles por negocio** vía `dbo.usuario_negocio` (usa `codrol_uneg`)

La función central de autorización es:
- `dbo.fn_authz_tiene_permiso(@codusr, @codneg, @clave_permiso)`
  Devuelve `1` si el usuario tiene el permiso:
  1) por permiso global directo (`usuario_permiso_global`)
  2) por rol global (`usuario_rol_global` + `rol_permiso`)
  3) por rol dentro del negocio (`usuario_negocio` + `rol_permiso`)

Soporta comodín:
- Permiso `*` (clave `*`) = acceso total.

---

### 2) Estructura de permisos recomendada
Convención de clave:
- `MODULO.ACCION` (simple) o `MODULO.SUBMODULO.ACCION` (granular)

Ejemplos:
- `NEGOCIO.VER`
- `INVENTARIO.MOVIMIENTO.CREAR`
- `FACTURACION.FACTURA.CERRAR`
- `RESERVAS.CREAR`
- `SEGURIDAD.RBAC.ADMIN`

### 4) Reglas de visualización (frontend)
Para cada módulo/feature:
1) Determinar `codusr` (usuario autenticado)
2) Determinar `codneg` seleccionado (si la app es multi-negocio)
3) Consultar permisos (idealmente desde API):
   - `GET /me/permissions?codneg=...` o equivalente
4) UI:
   - **Ocultar menú** si no tiene permiso *.VER del módulo
   - **Deshabilitar/ocultar acciones** según permisos de acción (CREAR/EDITAR/CERRAR/etc.)

Regla general:
- Si `fn_authz_tiene_permiso(codusr, codneg, '*')=1`, habilitar todo.

---

### 5) Semillas y SUPERADMIN
El script crea:
- Usuario `admin`
- Rol `SUPERADMIN`
- Permiso comodín `*`
- Asignación global `admin` -> `SUPERADMIN`

Esto permite que `admin` vea y opere todos los módulos.

    { "codrol": 3 }

- PATCH /negocios/:codneg/usuarios/:codusr/estado
  - Habilita/inhabilita un usuario dentro de un negocio (estado_uneg en usuario_negocio).
  - Requiere permiso: USUARIOS.ESTADO.CAMBIAR
  Body:
    { "estado": "I" }  // A o I

- PUT /negocios/:codneg/usuarios/:codusr/roles-creables
  - Configura roles que el usuario podrá asignar a sus descendientes.
  - Requiere permiso: USUARIOS.ROLES_CREABLES.CONFIGURAR
  - Requiere SP: dbo.sp_usuario_negocio_rol_creable_set
  Body:
    {
      "roles": [
        {"codrol": 2, "permitido": true},
        {"codrol": 3, "permitido": false}
      ]
    }

8) Notas importantes / limitaciones actuales
-------------------------------------------
- No existe endpoint público para refrescar access token aunque el método existe en TokenService.
- JWT secret está hardcodeado (Tokenpass.secret).
- El hashing de password es determinístico (IV fijo); útil para compatibilidad pero NO es un esquema recomendado para contraseñas en producción.
- Muchas validaciones y retornos dependen directamente del esquema y SPs/funciones definidas en la base de datos.

9) Flujo típico de uso (frontend)
--------------------------------
1) Login:
   - POST /auth/login con nombre/codusr + password.
   - Si eres trabajador sin loginmulti: enviar también codneg.

2) Si recibes `negocios` y deseas entrar a un negocio específico:
   - POST /auth/switch-negocio con codneg.
   - Guardar el nuevo accessToken.

3) Consumir endpoints del negocio:
   - Enviar Authorization Bearer <token>.
   - En endpoints que piden codneg, enviarlo y el backend valida pertenencia.
